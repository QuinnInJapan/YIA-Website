The site has a sound technical foundation. The best immediate work is to repair sitemap discovery, improve search-result copy, and correct a few content and URL inconsistencies. Separate English landing pages are the largest strategic opportunity if attracting English-speaking residents is a priority.

This report records the initial audit, before the subsequent implementation. No application code, CMS content, deployment, or account settings were changed during that audit.

## 1. Repair sitemap discovery

The live [robots.txt](https://yia.jp/robots.txt) contains `Sitemap: https://yia.or.jp/sitemap.xml`. A HEAD request to that destination returned **404**. The actual [sitemap](https://yia.jp/sitemap.xml) returned valid XML on `yia.jp`.

Change the directive to `https://yia.jp/sitemap.xml`. The local source contains the same error at [public/robots.txt](/Users/quinnngo/Desktop/projects/yia-nextjs/public/robots.txt:6). This does not mean the site is blocked from indexing: public crawling is allowed, internal links exist, and current pages appear in public search results. It is a broken discovery signal that is easy to repair.

After deployment, read robots.txt back and submit/check the correct sitemap in Search Console. [Google's sitemap guidance](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap) describes both submission paths.

## 3. Fix content accuracy and freshness cues

On the [Japanese conversation salon page](https://yia.jp/classes/conversation-salon), the English introduction calls the classes free. The same page lists fees for several adult groups and some children's options. A suitable direction is: “Japanese conversation classes for international residents, run by volunteer groups. Fees vary by group; see the schedule below.” Keep any genuinely free options labeled individually.

The footer on sampled pages says `Last Updated: 2026.03.02`, including September announcements. [SiteFooter](/Users/quinnngo/Desktop/projects/yia-nextjs/components/SiteFooter.tsx:35) uses one organization-level date. Remove that ambiguous global label, relabel its actual scope, or use meaningful page-specific update dates. Do not manufacture freshness by setting all pages to today's date.

The [Kids Festival announcement](https://yia.jp/announcements/kids-festival) has a Japanese closed-registration title while the English body says places remain for foreign residents. This may be an intentional audience-specific exception. State the distinction clearly in both languages before drafting metadata or availability markup; do not assume the event is canceled or universally sold out.

## 4. Complete the sitemap and use meaningful modification dates

The live sitemap contains **25 URLs**, with no announcement detail URLs and no `lastmod` values. Seven distinct announcement detail links are present in the sampled archive, including Kids Festival and the volunteer course. Their absence from the sitemap does not prevent discovery through links, but it is an avoidable omission for time-sensitive content.

[app/sitemap.ts](/Users/quinnngo/Desktop/projects/yia-nextjs/app/sitemap.ts:15) reads navigation routes and blog slugs only. Add published announcements whose destination is a detail page. Resolve each to its preferred slug URL, falling back to its ID only if needed. Exclude drafts and redirect-only announcements, and deduplicate destinations.

Add reliable modification dates for maintained content where the CMS can supply them. Ensure announcement publication, slug changes, and deletion invalidate the sitemap's dependencies under the existing on-demand revalidation design. Missing `lastmod` is not an error; adding accurate dates is an enhancement. Google ignores sitemap `priority` and `changefreq`, so tuning those values is not useful work. [Sitemap guidance](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap).

## 5. Normalize canonical identities and archive URLs

Two issues were found:

- **Live archive behavior:** `/announcements?page=2` and `?page=9999` both return 200 with an empty announcement list and canonicalize to `/announcements`. The current archive fits on one page, so page 2 is presently out of range. Return a proper 404 for out-of-range pages. When valid later pages exist, give each its own canonical URL. The same first-page canonical pattern exists in the blog index code, although the live sitemap currently has no blog posts. [Google's pagination guidance](https://developers.google.com/search/docs/specialty/ecommerce/pagination-and-incremental-page-loading) explicitly recommends self-canonicals for valid paginated pages.
- **Code-level announcement alias issue:** the detail route accepts both slug and document ID, generates static parameters for both, and constructs its canonical from the incoming parameter. A record with a slug can therefore have two canonical identities. Redirect ID aliases permanently to the preferred slug and derive metadata from that preferred URL. This is confirmed in code; the audit did not establish whether Google has indexed any ID aliases. [Detail route](/Users/quinnngo/Desktop/projects/yia-nextjs/app/(site)/announcements/[id]/page.tsx:26).

Relevant archive code: [AnnouncementsPageTemplate](/Users/quinnngo/Desktop/projects/yia-nextjs/components/templates/AnnouncementsPageTemplate.tsx:17), [category metadata](/Users/quinnngo/Desktop/projects/yia-nextjs/app/(site)/[category]/page.tsx:23), and [blog index](/Users/quinnngo/Desktop/projects/yia-nextjs/app/(site)/blog/page.tsx:20).

The Vercel project hostname also returns 200. Existing metadata points at `yia.jp`, which is helpful. Consider an HTML-page host redirect as a secondary cleanup, while preserving the `/api/revalidate` endpoint currently used by the production Sanity webhook. A blanket host redirect could disrupt that integration. There is no evidence here that the Vercel hostname is indexed.

## 6. Add structured data that matches the content

No JSON-LD appeared in any of the nine valid HTML samples, and a focused source scan found no `schema.org`, JSON-LD, or microdata implementation.

Start with `Organization` on the homepage: official Japanese and English names, abbreviation, canonical URL, logo, public phone/email, postal address, and verified official profile links. Those details already exist visibly. Add a visible breadcrumb trail and matching `BreadcrumbList` on nested pages. Organization markup helps Google distinguish the association and understand its details; it is not a guarantee of ranking gains. [Google's organization guidance](https://developers.google.com/search/docs/appearance/structured-data/organization).

For events, add `Event` only to pages focused on an individual event, with verified start/end time, venue/address, organizer, image, and applicable booking details. The Japan Festival page currently lists several separate dates/programs; retain it as an overview and link to individual event pages where worthwhile. Existing announcement pages may be suitable event landing pages, avoiding unnecessary duplicates. Keep registration availability distinct from cancellation status. [Google's event requirements](https://developers.google.com/search/docs/appearance/structured-data/event).

Use article-specific metadata and `BlogPosting` when the blog is active. The shared social helper currently uses `og:type=website` and one organization image for every route. Per-event/article images are a useful sharing improvement, with the existing image as fallback.

## 7. Build on the useful service content already present

The salon schedule and counseling timetable already render as HTML, which is a strength. Extend that approach to details still delegated to flyers:

- Foreign-language courses: publish the current term, individual class days/times, level, enrollment status, and how to choose a class alongside the existing fees and application instructions.
- Volunteer course: bring venue, eligibility, fees if any, and contact/application details onto the page after checking the current flyer.
- Event pages: show the next occurrence, audience, venue, access, deadline, and booking status prominently; link between the evergreen program page and its current announcement.
- Add concise answers to real questions such as beginner suitability, enrollment midway through a term, fees, and support languages. Only state answers that the association can maintain accurately.

Suggested topic groups to validate in Search Console are Japanese classes in Yokosuka, foreign-language courses, multilingual resident support, cultural events, and volunteering. Build substantial pages around distinct needs; avoid making near-identical pages for keyword variants.

The [city's association listing](https://www.city.yokosuka.kanagawa.jp/0535/sisetu/fc00000023.html) already provides consistent address and phone details, and the [city's Japanese-class FAQ](https://www.city.yokosuka.kanagawa.jp/faq/shisei/diversity/kokusai/0691.html) references YIA. Review important partner links and the existing Business Profile for accuracy; request relevant direct service-page links when appropriate. No partner outreach was performed.

## 8. Treat English SEO as a separate landing-page opportunity

Sampled pages use Japanese titles, Japanese canonicals, and `html lang="ja"`, with English text alongside Japanese. That English text is present in the HTML; it should not be described as wholly invisible to search engines. The Translate widget changes the current page using cookies and JavaScript and does not create independent language URLs.

If English acquisition is important, pilot `/en/` equivalents for the homepage, Japanese classes, counseling, and the major cultural event. Each should have English navigation/body, an English title and description, a self-canonical, a reciprocal `hreflang` relationship to its Japanese counterpart, and a visible language link. Add language alternates only for real equivalent pages. Keep the existing Japanese URLs stable.

The blog language tabs are another code-level limitation: they initially render the Japanese body and replace it on click, without a separate English URL. Address this when publishing English blog content. [Google's multilingual guidance](https://developers.google.com/search/docs/specialty/international/managing-multi-regional-sites) recommends distinct URLs for language versions and warns that dynamically selected variants may not all be crawled.
